================================================================
 0. LA DECISION QUE DEFINE TODO EL PROYECTO
================================================================

El 90% de los que hacen esta prueba se equivocan aca, y no es por
React: es por no leer la letra chica de la API.

FakeStoreAPI NO PERSISTE ESCRITURAS. Concretamente:

  OPERACION              QUE DEVUELVE            APARECE EN UN GET
  ------------------------------------------------------------------
  POST /products         Objeto producto con id  NO
  PUT /products/:id      El objeto "actualizado" NO (sigue el original)
  DELETE /products/:id   El objeto "eliminado"   SI (sigue existiendo)

CONSECUENCIA PRACTICA: si despues de crear un producto haces
GET /products para "refrescar la lista", tu producto desaparece.
Si borras y volves a pedir la lista, el borrado reaparece. La
interfaz se contradice a si misma y ahi perdes puntos en
"experiencia coherente durante la sesion".

Hay dos modelos y solo uno sirve:

MODELO A - "La API es la fuente de verdad"
  Cada escritura -> refetch. Es el reflejo natural y esta MAL para
  esta API. Produce el bug de arriba.

MODELO B - "React es la fuente de verdad de la sesion; la API confirma"
  - GET /products UNA SOLA VEZ al montar: es la semilla del estado.
  - Cada escritura: await la request y, SI RESPONDE OK, actualizas
    tu array local con lo que ya sabes.
  - La respuesta HTTP se usa como confirmacion de que la operacion
    fue aceptada, no como la nueva verdad.

Este es el concepto central del ejercicio:
ESTADO DEL SERVIDOR vs. ESTADO DE LA SESION.
Hay que poder decirlo con estas palabras en la revision.


VERIFICA LAS LIMITACIONES VOS MISMO, NO ME CREAS

Antes de escribir una linea de React, proba los endpoints con curl

- Que id devuelve un POST? Hay reportes de que SIEMPRE devuelve el

 1. MODELO DE ESTADO
================================================================

Antes de crear archivos, dibuja en papel que estado necesitas y
DONDE VIVE. Regla: el estado vive lo mas arriba posible del arbol
que lo necesite, y lo mas abajo posible del que no.

  ESTADO                          DONDE                  POR QUE
  ---------------------------------------------------------------------
  products (array)                App                    Lo consumen lista,
                                                         contadores, filtros
  status de la carga inicial      App                    La pantalla entera
                                                         depende
  error de la carga inicial       App                    Idem
  Operacion en curso (id + tipo)  App                    Deshabilita botones y
                                                         muestra spinner por fila
  Busqueda y categoria            App o contenedor       No los necesita el
                                                         formulario
  Campos del formulario + errores DENTRO del formulario  Nadie mas los necesita
  Modal abierto / modo / producto App                    Coordina lista +
                                                         formulario + confirmacion
  Toast / mensaje de exito        App                    Es global

TRES REGLAS QUE TE VAN A PREGUNTAR
----------------------------------------------------------------

1) NO GUARDES ESTADO DERIVADO.
   La lista filtrada, las categorias disponibles y los contadores se
   CALCULAN EN EL RENDER a partir de products. Si los guardas en
   useState, tenes dos verdades que se desincronizan (creas un
   producto y el contador no sube -> bug clasico).

2) UN SOLO ESTADO, NO CINCO BOOLEANOS.
   En vez de isLoading, isError, isEmpty, isReady (que permiten
   combinaciones imposibles como "cargando y con error"), usa un
   estado unico tipo: 'idle' | 'loading' | 'ready' | 'error'.
   Modelar estados como una maquina evita pantallas contradictorias
   y suena muy bien cuando lo explicas.

3) EL MODAL NO NECESITA isEditing + selectedProduct SUELTOS.
   Un solo valor que codifique el modo alcanza:
     null       -> cerrado
     'create'   -> alta
     un producto-> edicion
   Una variable, un estado valido por caso. Si tenes dos booleanos,
   tarde o temprano queda isOpen:true con isEditing:true y producto
   null.


================================================================
 2. useEffect: CUANDO SI Y CUANDO NO
================================================================

Este es el punto donde mas se nota si entendiste React o copiaste.

useEffect sirve para SINCRONIZAR CON SISTEMAS EXTERNOS AL ARBOL DE
REACT (red, DOM, timers, localStorage). No es un "onMount" ni un
"watch".

USALO PARA:
  - El fetch inicial de productos. Es el caso legitimo y
    probablemente el unico obligatorio.
  - Cerrar el modal con Escape o bloquear el scroll del body.
  - Autocerrar un toast despues de N segundos (con cleanup que
    limpie el timer).

NO LO USES PARA:
  - Calcular la lista filtrada -> se calcula en el render.
  - Actualizar products despues de crear/editar/borrar -> eso va EN
    EL HANDLER, despues del await. Si lo haces con un efecto que
    "mira" un flag, vas a terminar con doble render y un bug de
    sincronizacion.
  - Copiar props a estado del formulario -> usa la key del componente
    o inicializa desde props con intencion.

EL ARRAY DE DEPENDENCIAS
----------------------------------------------------------------
  []  = se ejecuta una vez al montar (en desarrollo, DOS VECES).
  Si el efecto usa una variable y no la declaras, tenes un closure
  viejo. El linter (eslint-plugin-react-hooks) te va a gritar:
  escuchalo, no lo silencies.
  Definir la funcion de fetch adentro del efecto o afuera del
  componente: si la defines afuera y no la memoizas, cambia de
  identidad en cada render y tu efecto se dispara en loop. Esa es
  una de las causas mas comunes de "la API me esta rateando".

STRICTMODE: EL DOBLE EFECTO ES UNA FEATURE
----------------------------------------------------------------
En desarrollo, React monta, desmonta y remonta tus componentes para
que descubras efectos sin cleanup. Si ves DOS GET en la pestaña
Network, no esta roto: te esta avisando. La solucion no es borrar
StrictMode; es CANCELAR EL EFECTO AL DESMONTAR (AbortController o un
flag cancelled) y no setear estado si ya no estas montado. Eso ademas
evita el warning de memory leak y una condicion de carrera real.

  Pregunta tipica: "por que ves dos requests en desarrollo y uno en
  produccion?" Si respondes "por StrictMode, y lo manejo con
  cancelacion", cerraste el tema.


================================================================
 3. FORMULARIOS
================================================================

- INPUTS CONTROLADOS: value desde estado + onChange. Cada tecla
  actualiza el estado. Es mas codigo que useRef, pero es el que te
  permite validar en vivo, mostrar errores y resetear.

- UN OBJETO DE ESTADO PARA EL FORMULARIO o un useState por campo:
  los dos son validos. El objeto escala mejor; los campos sueltos
  son mas simples de leer. Elegi y SABE JUSTIFICAR EL TRADEOFF.

- LA VALIDACION ES UNA FUNCION PURA. Entra el formulario, sale un
  objeto de errores ({ title: '...', price: '...' }). Nada de
  alert(). Pura = testeable = facil de explicar.

- CUANDO VALIDAR: al enviar (siempre) y, si queres, al salir del
  campo (blur) o al corregir un campo que ya tenia error. Validar en
  cada tecla desde el segundo 0 es agresivo y se siente mal.

- REGLAS MINIMAS RAZONABLES: titulo requerido y con largo minimo,
  precio numerico y mayor a 0 (y que no sea NaN, que es lo que
  devuelve parseFloat de basura), categoria de una lista cerrada,
  descripcion con largo minimo, imagen opcional con fallback visual.

- NO TE APOYES SOLO EN required / type="number" DEL HTML. Sirven
  como red de seguridad, pero el evaluador va a querer ver tu logica
  y tus mensajes. Ademas, un type="number" vacio te llega como
  string "" y te rompe las cuentas si no lo convertis.

- RESET vs PREFILL: para editar, el formulario se abre con datos.
  Para crear, vacio. La forma mas limpia de "reiniciar" un componente
  con estado interno es CAMBIARLE LA KEY desde el padre. Es un truco
  que vale oro y demuestra que entendes el ciclo de vida.


================================================================
 4. LOS TRES FLUJOS, EN PALABRAS
================================================================

Escribilos asi en papel antes de programar. Cada paso tiene un
porque.

CREAR
----------------------------------------------------------------
1. Usuario envia -> validas. Si hay errores: mostras mensajes y
   CORTAS. No hay request.
2. Marcas operacion en curso -> el boton se deshabilita (evita el
   doble submit, que es el bug #1 de los CRUD).
3. POST con el body limpio.
4. CHEQUEAS response.ok (ver seccion 7: fetch NO lanza en 4xx/5xx).
5. Si OK: agregas el producto al array local con un id unico ->
   cerras modal -> toast de exito.
6. Si falla: EL MODAL QUEDA ABIERTO CON LOS DATOS CARGADOS, mostras
   el error. Perder lo que escribio el usuario es imperdonable.
7. finally: apagas el estado de "en curso", pase lo que pase.

EDITAR
----------------------------------------------------------------
1. Precargas el formulario con el producto.
2. Mismo camino de validacion.
3. PUT -> si OK, reemplazas POR ID en el array (no por indice: el
   indice cambia si hay filtros o borrados).
4. Si el producto editado ya no cumple el filtro activo (le
   cambiaste la categoria), va a "desaparecer" de la vista. ESO ES
   CORRECTO, pero el usuario necesita un toast que lo explique. Ese
   detalle es oro en la evaluacion.

ELIMINAR
----------------------------------------------------------------
1. Click en borrar -> ABRE CONFIRMACION, nunca window.confirm (no es
   estilizable, no es responsive y se ve pobre).
2. La confirmacion dice QUE vas a borrar (el nombre), no "estas
   seguro?" generico.
3. Mientras borra: spinner en ESA FILA, no en toda la pantalla.
4. Si OK: sacas del array por id.
5. Si falla: el producto SIGUE AHI y mostras el error. Nunca saques
   optimistamente sin poder revertir.

================================================================
 7. ERRORES: LA TRAMPA QUE SE LLEVA A MEDIO CURSO
================================================================

fetch SOLO RECHAZA si falla la red (sin conexion, DNS, CORS).
Un 404 o un 500 RESUELVEN LA PROMESA NORMALMENTE. Si tu try/catch
no mira response.ok, tu app va a mostrar "Producto creado" cuando el
servidor devolvio un 500.

TAXONOMIA QUE TENES QUE DISTINGUIR Y COMUNICAR DISTINTO
----------------------------------------------------------------
1. Red caida / timeout -> "No pudimos conectar. Revisa tu conexion."
2. HTTP 4xx/5xx -> "El servidor rechazo la operacion." (loguear status)
3. Respuesta con forma inesperada -> JSON invalido o sin los campos
   que esperas. response.json() tambien puede fallar.
4. Validacion -> NO ES UNA EXCEPCION, es flujo normal del formulario.

Y algo que suma: DESHABILITAR ACCIONES mientras hay una operacion en
curso y, si queres ser prolijo, un timeout con AbortController (si la
API no responde, no dejas al usuario esperando para siempre).

justamente porque tu estado es local. Si lo haces, explica que es

 11. PREGUNTAS DE LA REVISION TECNICA
================================================================

PREPARALAS DE VERDAD.

- "Por que no haces refetch despues de crear?"
  -> Modelo B, la API no persiste, y el refetch borraria el cambio.

- "Donde esta la fuente de verdad?"
  -> products en App, sembrado una vez por el GET.

- "Para que usaste useEffect y que pasa si lo sacas?"
  -> Sin el no hay carga inicial; si lo usas para derivar, explica
     por que esta mal.

- "Que pasa si el POST devuelve 500?"
  -> No toco el estado, muestro error, dejo el modal abierto, no
     pierdo los datos.

- "Como evitas el doble submit?"
  -> Deshabilito por estado de operacion en curso.

- "Por que la lista filtrada no esta en useState?"
  -> Estado derivado, se calcula en render.

- "Que pasa si borro el ultimo producto de la pagina 3?"
  -> Ajuste de pagina / vuelta a la anterior.

- "Agrega un campo stock ahora."
  -> Si tu codigo esta bien separado, tocas 4 lugares: tipo de dato,
     validacion, input, render. Si tocas 15, tenes un problema de
     diseno.


================================================================
 12. TRAMPAS QUE BAJAN NOTA
================================================================

- Refetch despues de cada escritura (el error #1 de esta prueba).
- Guardar derivados en estado.
- Un useEffect por cada cosa, incluido "actualizar el array cuando
  cambia un flag".
- No chequear response.ok.
- Confiar en el id que devuelve el POST.
- key={index} al renderizar listas que se pueden borrar o filtrar.
- Mutar el array (push, splice, sort in-place) en vez de crear uno
  nuevo. React no ve el cambio.
- Comparar precios como string ("10" < "9" es true).
- alert() / window.confirm().
- Perder los datos del formulario cuando falla la request.
- Un spinner global que bloquea toda la app por borrar una tarjeta.
- Mezclar ingles y espanol en la UI.
- useEffect sin cleanup en el fetch -> warning y doble set de estado.


================================================================
 13. README: QUE DOCUMENTAR DE LA API
================================================================

No alcanza con "no persiste". Escribi:

- Que endpoints usaste y con que metodo.
- Que las escrituras son simuladas y no persisten entre sesiones.
- Que por eso el estado de la sesion vive en React y se pierde al
  recargar (y que recargar es, literalmente, tu "reset").
- Que un GET posterior no refleja POST/PUT/DELETE.
- El tema del id que devuelve el POST.
- Las categorias tal cual vienen de la API, con sus particularidades
  de escritura.
- Que no hay autenticacion ni paginacion real en el servidor (si usas
  paginacion, es client-side).
